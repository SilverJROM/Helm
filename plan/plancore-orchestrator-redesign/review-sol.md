## VERDICT: NEEDS-REVISION

The requirements have the correct authorship goal but the wrong convergence protocol and an unresolved coordinator ownership split. R2.7 is not a reliable analogue of B5: B5 binds a verdict to one immutable artifact, whereas R2.7 asks independent stochastic authors to manufacture the same bytes without a canonical target. R2.8 admits a deterministic two-cycle, R2 hashes only one of the two jointly authored canonical documents, R1 and R2 assign the same relay work to different owners, and the retained plancore model seat has no actual control mechanism. Implementation planning should not begin until the contract is replaced with a linear, immutable candidate-and-signature protocol over the complete artifact bundle and the initial-planning plancore model seat is retired in favor of engine-owned coordination.

## R2.7 CONVERGENCE DEFINITION — achievable as written, or needs a different mechanism?

It needs a different mechanism. Byte identity is a sound property **after there is one immutable candidate**; it is not a sound way to ask two independent generators to create that candidate. The existing B5 mechanism has exactly that asymmetry: every reviewer signs the current canonical `plan.md` hash, freshly recomputed by the engine (`src/services/planning-phase-service.ts:1002-1008`, `:1087-1107`). R2.7 removes the shared target while retaining the hash comparison, so it does not inherit B5's convergence property.

R2.8 can oscillate even if both seats follow the prompt perfectly:

1. Round 1 produces A=`a` and B=`b`, with different hashes.
2. Fresh A2 is shown B's draft and adopts it byte-for-byte; fresh B2 is shown A's draft and adopts it byte-for-byte. The outputs are now A2=`b`, B2=`a`: still different, merely swapped.
3. Round 3 repeats the same instruction and returns A3=`a`, B3=`b`. The protocol has entered a perfect two-cycle. If either seat instead “improves” the other draft, ordinary formatting, ordering, or phrasing changes create the same non-convergence without an exact swap.

Fresh seats make this more likely because the current mechanism has no `transport.send`; every later opinion is a new spawn with a new correlation id (`src/services/planning-review-round.ts:483-505`, `:605-616`). Showing each fresh seat only “the other's” draft also discards its predecessor's rationale. A round cap bounds the cost but does not make this a convergence protocol; it converts normal substantive agreement into `BLOCKED`.

Replace R2.7-R2.9 with a linear candidate protocol:

1. Round 1 remains a blind draft round. Every configured co-planner submits a complete, immutable artifact bundle: `og-requirements.md` plus `plan.md`.
2. The engine chooses a proposer by a deterministic rule fixed before outputs are visible (for example, lowest configured slot). A fresh proposer receives **all** blind drafts and authors candidate version C1. The candidate is frozen under a manifest hash covering both files, their lengths/paths, the round, and dispatch identity.
3. Every other co-planner receives the same immutable C1 and may only `SIGN <candidate-hash>` or `REJECT <candidate-hash> <structured defects>`. The engine recomputes the hash and accepts only signatures from all required configured seats against that exact bundle.
4. On rejection, exactly one fresh proposer receives C1 plus the complete defect set and authors C2. No ratifier writes a competing candidate. Then fresh ratifiers sign or reject C2. The proposer can rotate by a predetermined slot order without creating parallel heads.
5. Agreement is all required ratifiers signing one current bundle hash; only then does the engine atomically promote those exact two files to canonical paths and ingest them. Exhausting the cap remains visible `BLOCKED`, with candidate hash, signer set, and outstanding structured defects.

This does reintroduce sign-off, but it does **not** restore plancore authorship or reduce co-planners to reviewers of plancore prose. The blind drafts, candidate revisions, and blocking defect decisions all come from co-planners. The asymmetry is the protocol feature that creates one version history instead of two oscillating heads.
